# 医院门诊挂号与缴费系统需求分析

## 1. 项目概述

### 1.1 项目背景

医院门诊在集中放号时可能出现短时大量挂号请求，患者也需要在挂号、缴费、报到、候诊、诊疗和取药等环节之间反复查询信息。若号源扣减、重复请求和缴费状态处理不一致，可能造成超卖、重复挂号或业务记录不完整。

本项目面向软件工程专业的软件体系结构综合实训，构建一个可在本机运行的门诊业务教学系统。系统用事务、数据库行锁、条件更新、唯一约束和请求幂等处理挂号一致性；以患者、医生、收费员、药师和管理员的角色串联门诊核心流程。缴费使用模拟支付，不接入真实支付渠道。

### 1.2 项目目标

1. 提供科室、医生、医生排班和号源的管理与查询。
2. 支持患者查询未来可预约号源、挂号、缴费、取消、退号和报到。
3. 支持医生候诊队列、叫号、接诊、提交电子病历和开具处方。
4. 支持药品目录、库存调整、处方缴费、库存预占和发药。
5. 以事务和幂等控制保证高并发请求下的号源及业务状态一致。
6. 展示 Maven、Spring、Spring MVC、MyBatis、Vue 3 和 MySQL 等课程要求技术的协作方式，并提供可选 Redis 队列与 Quartz 排班模板扩展。

### 1.3 项目范围与限制

本系统为教学演示项目，运行配置以 IntelliJ IDEA、本机 MySQL 和 Navicat 为主。系统不连接真实医保、医院 HIS、短信平台或支付网关，不承担真实诊疗、处方审核、收费结算或患者健康数据管理职责。演示患者、病历和处方均为虚构样例。

## 2. 用户角色与权限

| 角色 | 主要职责 | 主要权限 |
| --- | --- | --- |
| 患者（PATIENT） | 完成预约和就诊前后操作 | 查询排班；本人挂号、缴费、取消或申请退号；就诊当天报到；查看本人账单、病历和处方 |
| 医生（DOCTOR） | 管理本人排班的就诊流程 | 查看本人排班和候诊队列；叫号、开始接诊、过号处理；填写病历、完成接诊和开具处方 |
| 收费员（CASHIER） | 协助处理收费业务 | 查询门诊账单；执行模拟缴费或按业务规则办理退款 |
| 药师（PHARMACIST） | 维护库存并处理发药 | 查看药品与库存；调整库存；核对已缴费处方并发药；查看库存流水 |
| 管理员（ADMIN） | 维护系统基础资料并监督业务 | 管理账号、科室、医生、排班和药品；查询业务统计与操作审计；处理停诊相关业务 |

用户必须通过认证后访问受保护功能。服务端按角色和资源归属检查权限；患者只能访问自己的业务数据，医生只能处理自己的医生身份和排班相关业务。

## 3. 功能需求

### 3.1 账号与权限管理

- 系统应支持登录、退出和患者注册，并保存密码的安全哈希，不保存明文密码。
- 系统应按患者、医生、收费员、药师和管理员角色控制接口权限。
- 管理员应能够创建账号、停用账号，并为用户配置对应业务身份。
- 对病历、账单、处方等个人数据，系统应执行患者归属和医护角色校验。

### 3.2 科室、医生与排班管理

- 管理员应能够维护科室名称、位置和启用状态，以及医生的科室、职称、专长和启用状态。
- 管理员应能够创建和维护医生排班，设置工作日期、时段、起止时间、号源总数和挂号费用。
- 同一医生的排班不得发生时段重叠；已开始的排班不得新建；已有有效挂号的排班不得随意更改日期或时间。
- 患者应能够按科室、医生、职称、日期和时段筛选排班，并可选择只看有余号的排班。
- 患者预约目录只显示当前至未来六天（共七个自然日）内尚未开始且开放的排班。
- 演示模式应在启动时及每天上海时间 00:05 为演示医生补齐未来七天缺失的排班；不得覆盖已有、停诊、人工维护或与现有时段重叠的排班。非演示环境可使用管理员维护的排班或可选的 Quartz 模板生成能力。

### 3.3 在线挂号与退号

- 患者应能够选择开放且尚未开始的排班发起预约。
- 挂号成功后应创建挂号记录和对应的挂号费账单，并占用一个号源。
- 未缴费预约的保留时间最长为 15 分钟，且不得超过排班开始时间；超时或患者取消时应关闭预约并释放号源。
- 同一患者不得在同一排班重复保留有效挂号。
- 患者已缴费且尚未开诊、尚未报到时，可按规则申请退号退款；开诊或接诊后不得由患者自行退号。医院停诊时由管理员处理相关业务。
- 每个挂号请求应携带请求幂等键；重复提交同一请求不得重复扣减号源或创建多笔业务。
- 并发挂号必须在数据库事务中完成最终校验与号源扣减。系统应使用行锁、条件更新和唯一约束共同防止超卖及重复预约；Redis 队列仅为可选的请求缓冲层，不是号源最终一致性的依据。

### 3.4 门诊缴费

- 系统应为挂号费和处方药费创建独立账单，并展示账单状态、金额和截止时间。
- 患者只能支付本人有效且未过期的账单；已关闭、已退款或已超时账单不得支付。
- 支付成功后应更新账单及关联业务状态，并记录唯一交易号；重复支付请求应保持幂等。
- 处方缴费时，应在同一事务内校验处方状态和药品可用库存，并按处方明细预占库存；任一药品库存不足时整笔操作回滚。
- 项目支付为模拟支付，不应向用户暗示发生了真实扣款。

### 3.5 报到、候诊与接诊

- 已支付挂号的患者应可在就诊当天、排班开始前 30 分钟至排班结束前完成报到。
- 报到成功后系统应为患者分配候诊队列号；相同挂号重复报到不得生成重复就诊。
- 对应医生应能查看和处理本人排班的候诊队列，执行叫号、开始接诊、过号、重新排队和完成接诊等操作。
- 系统应记录重要队列事件及操作者，便于查看就诊过程。
- 医生不得处理其他医生的排班或就诊记录。

### 3.6 电子病历与处方

- 医生接诊时应能够填写主诉、现病史、既往史、过敏信息、诊断、医嘱和处方明细。
- 病历应区分草稿与已提交状态；病历和处方应关联患者、医生、就诊记录及原挂号。
- 医生完成接诊后，患者应能够查询本人已提交的病历和处方。
- 系统生成的演示病历及处方必须明确标为虚构教学数据，不构成医疗建议。

### 3.7 药房与库存管理

- 管理员应能够维护药品编码、名称、规格、单位、价格、启用状态和库存预警阈值。
- 药师应能够进行有原因说明的库存增减，且调整后库存不得低于已预占数量。
- 药师只能对有效且已缴费的处方执行发药；发药完成后应扣减实际库存并记录库存流水。
- 退款或处方作废时，应按业务状态释放相应的预占库存；已发药处方不得按未发药流程重复处理。
- 系统应支持查询当前库存、可用库存、低库存药品及库存变动记录。

### 3.8 管理统计与审计

- 管理员应能够查询当日挂号数、已完成就诊数、收入、退款、净收入、科室统计和低库存提示。
- 系统应记录挂号、退号、缴费、退款、发药及关键管理操作的操作者、结果和时间。
- 查询接口应支持分页及项目已提供的动态筛选条件。

### 3.9 可选高峰与排班扩展

- **Redis Streams 挂号队列（可选）**：高峰期可先受理并缓冲请求，患者可查询处理状态；入队不代表挂号成功，实际挂号仍由数据库事务校验。
- **Quartz 排班模板（可选）**：管理员维护按星期重复的排班模板后，任务可按配置定时补齐未来七天排班，并记录生成、跳过或失败结果。
- 默认演示流程仅依赖 MySQL；Redis 与 Quartz 扩展默认关闭。

## 4. 核心业务规则与流程

### 4.1 挂号及缴费状态

```text
患者提交预约
  → 检查账号、排班状态、开诊时间、重复预约和余号
  → 事务内扣减一个号源并创建 RESERVED 挂号与 UNPAID 账单
  → 模拟支付成功：挂号变为 BOOKED，账单变为 PAID
  → 模拟支付失败、超时或患者取消：关闭挂号并释放号源
```

重复请求通过幂等键识别。号源扣减、挂号记录和账单创建必须作为一个事务提交；事务失败时应整体回滚。

### 4.2 就诊及处方流程

```text
已缴费患者在规定时间报到
  → 进入对应医生候诊队列
  → 医生叫号并开始接诊
  → 保存并提交电子病历、处方
  → 患者模拟缴纳药费并预占药品库存
  → 药师核对处方并发药，记录库存出库流水
```

### 4.3 时间口径

- 后端业务时钟和定时任务统一使用 `Asia/Shanghai`；数据库和 JSON 时间格式按项目配置处理。
- 挂号可用性及七日窗口以服务端当前时钟为准，不能只依赖浏览器显示或客户端传入时间。
- 历史排班、挂号、缴费和就诊记录保留实际发生日期；滚动补班只补未来缺项，不改写历史。

## 5. 数据需求

| 数据实体 | 主要内容 |
| --- | --- |
| 用户与患者档案 | 登录名、密码哈希、角色、启用状态、患者联系方式及过敏信息 |
| 科室与医生 | 科室位置和状态；医生账号、科室、职称、专长和状态 |
| 排班 | 医生、日期、时段、起止时间、总号源、剩余号源、费用、状态和来源 |
| 挂号与账单 | 患者、排班、请求幂等键、业务状态、保留截止时间及账单状态 |
| 支付与退款 | 账单、金额、交易号、办理人、原因及发生时间 |
| 就诊与队列事件 | 挂号、医生、候诊号、就诊状态、叫号及接诊时间 |
| 病历与处方 | 患者、医生、就诊、病历内容、处方状态和药品明细 |
| 药品与库存流水 | 药品价格与库存、预占数量、调整/出入库类型、数量、操作人及原因 |
| 操作审计与任务记录 | 操作名称、操作者、成功状态、时间；可选排班生成任务结果 |

所有业务关系通过主键和外键关联。数据库使用唯一约束、状态字段及事务规则维护有效挂号、交易号、队列号和处方等业务唯一性。

## 6. 非功能需求

### 6.1 一致性与并发

- 多个患者同时抢同一号源时，成功挂号数不得超过可用号源。
- 重复 HTTP 请求、客户端重试或队列重试不得产生重复挂号、支付或扣库存。
- 涉及号源、账单、库存和处方状态的多表变更应使用事务，并在失败时回滚。
- Redis 队列处理应保留数据库最终校验；系统不能将“请求已入队”显示为“挂号已成功”。

### 6.2 安全与隐私

- 密码需使用安全哈希存储；敏感接口需认证、角色校验及业务数据归属校验。
- 对会话和状态变更请求实施项目配置的 CSRF 防护。
- 真实数据库密码、密钥和本机私有配置不得提交到版本库。
- 电子病历属于敏感信息，查询范围应限制为本人或授权医护人员。教学数据不得用于真实诊疗。

### 6.3 可维护性与易用性

- 后端采用分层结构，Spring 管理依赖与事务，Spring MVC 提供 REST 接口，MyBatis 负责持久化及动态 SQL。
- 前端应提供明确的加载、空数据、错误和业务状态反馈，并支持常见筛选和分页。
- 初始化 SQL 与 IDEA 本机运行说明应随项目提供；演示数据初始化应可重复运行且不重置已有业务资料。

### 6.4 性能边界

本项目用于课程综合实训和本机演示，不承诺医院生产环境的吞吐量、可用性或灾备指标。高并发正确性以数据库并发事务和约束保障；如需评估具体容量，应另行定义并执行压力测试。

## 7. 技术与部署约束

| 技术 | 项目用途 |
| --- | --- |
| Maven | 后端模块依赖管理、编译和打包 |
| Spring Boot / Spring | 整合启动、依赖注入、事务和 AOP 审计 |
| Spring MVC | REST API、参数校验和统一异常处理 |
| MyBatis | Mapper 数据访问、动态 SQL 查询 |
| Vue 3 | 患者、医生、药房和管理端页面 |
| MySQL 8 | 业务数据、约束、事务和行级并发控制 |
| Navicat | 本机 MySQL 可视化管理工具，不是数据库服务器 |
| Redis Streams（可选） | 挂号高峰请求缓冲 |
| Quartz（可选） | 基于排班模板的定时生成 |

项目本机运行需 JDK 17 或 21、Maven 3.9.x、Node.js 兼容版本、MySQL 8 和 IntelliJ IDEA。后端和前端分别运行，前端通过开发代理访问后端 API。

## 8. 验收标准

1. 不同角色只能访问各自授权的功能和业务数据。
2. 患者能够查询当前日期起七天内的未来开放排班，过期排班不出现在可预约列表。
3. 同一排班号源不足时挂号被拒绝；并发测试中成功挂号数不超过初始号源数，重复幂等请求不重复占号。
4. 未支付预约可取消或超时释放号源；已支付挂号按退号规则处理，支付与退款记录可查询。
5. 患者可在规定时间报到，医生可处理本人队列并保存病历、完成接诊和开具处方。
6. 药品库存不足时处方缴费预占失败且事务回滚；发药、库存变更和流水记录一致。
7. 演示模式启动及每日任务能补齐未来七天缺失排班，重复执行不会复制已有时段或覆盖人工数据。
8. 项目可按运行指南在 IDEA、Vue 开发服务器和 MySQL 环境中启动；项目测试及前端构建通过。

## 9. 后续可扩展方向

- 将模拟支付替换为带签名校验、异步回调和对账机制的支付适配层。
- 为可选 Redis 队列补充积压监控、失败重试、死信处理和压测方案。
- 使用排班模板、节假日规则、医生请假和停诊流程完善排班管理。
- 为生产部署补充环境隔离、HTTPS、密钥管理、备份恢复、审计保留策略和可观测性。
